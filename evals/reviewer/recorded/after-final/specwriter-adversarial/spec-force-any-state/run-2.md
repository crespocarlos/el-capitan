**Critical**

**Acceptance criterion 1 ("closes a task in any state but DONE as DONE")**: This lets a DRAFTING task become DONE without Gate 1 approval. The Summary says "only an APPROVED spec may be implemented, and a DONE task with a PR is read as shipped, approved work." A literal build lets a never-approved spec go from DRAFTING to DONE with a GitHub PR URL. That task then looks like shipped, approved work and is indistinguishable from a genuinely approved one. Fix: decide whether dropped or unapproved tasks close as DONE or as ABANDONED. If DONE stays, add a criterion that a close from a pre-APPROVED state is recorded as not approved and not shipped, and never sets the approval marker. Put the choice under `## Open questions` as `[NEEDS CLARIFICATION: should dropped or never-approved specs close as ABANDONED instead of DONE?]`.

**Acceptance criterion 1 ("`--pr-url <value>` … The value is logged … as the reason")**: The `--pr-url` flag is overloaded as a free-text reason, and "a GitHub PR URL is also added to the task's PR list" does not define how a URL is told from text. Input such as `--pr-url "dropped"` is logged as a reason. Input such as `--pr-url https://evil/x/pull/1` could be treated as a PR. A close with no PR can also still say nothing. The spec does not say whether the flag is required, how "GitHub PR URL" is validated, or what happens when the value is empty. Fix: use a separate `--reason` flag, or define the validation rule and the empty-value behaviour in the criterion.

**Important**

**Acceptance criterion 3 ("A forced close ends an open BLOCKED line")**: It is unclear what "ends" means, and whether it applies to a close from a state with no BLOCKED line. A builder might delete the line, which loses history. They might append a closing entry, or they might error when there is no line to end. Fix: say that the BLOCKED line is closed with a timestamped entry that keeps the history, and that a close with no open BLOCKED line succeeds.

**Acceptance criterion 2 ("every row that is not DONE")**: This includes ABANDONED rows, so a task that "only the owner sets" as abandoned can be reopened as DONE. The spec does not say whether that is intended. It also does not say whether the TUI closes the same set of states as the CLI, or whether the "note prompt" is required and where the note goes. If the note feeds the same reason field, an empty note gives an empty reason. Fix: state explicitly whether ABANDONED is closable, and that the TUI note uses the CLI's reason and validation.

**Acceptance criteria (whole list)**: Nothing says what must stay impossible. Without `--force`, `mark-done` from non-IMPLEMENTING states must still be rejected. A non-owner must not be able to force-close. DONE must remain terminal, with a second close a no-op or an error rather than a duplicate PR entry. Fix: add criteria for each of these, including that the existing non-force behaviour is unchanged and what happens when an agent rather than the owner runs `--force`.
