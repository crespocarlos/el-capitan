Measured 2026-10-26 on c0 (7 days, 457 discovery agent runs, 160 recent conversations) plus the Kibana code at c0's build (identical to our base for `run_agent/`).

**CORRECTION (2026-10-27, trace-803a970e… from c0, gpt-6-luna-pro, 23.6 min, 7 rules, old parallel-sample prompt):** calls ran at 149k, 179k, 376k, 391k, 410k with NO compaction; compactions came at ~407-410k, 472k, 501k, 425k, each followed by a full restart (load_skill x5, 82k-char ki_search x4, 7 parallel samples x4, ~221k chars each = +100-200k reported tokens). That is NOT a 128k window (102k line); best fit is compaction line ~410k with the 5-cycle cooldown (0.8 x ~512k), origin unknown. So item (1) below (gpt-6-luna-pro falls to the 128k default) is NOT supported by this trace or by the pasted 3-rule run; treat the whole chain as a hypothesis. What this trace does show: the single-cycle 7-sample dump is what jumps the context 150k-200k per restart, and each compaction forces the full reload. The window source at c0 remains unidentified.

**ROOT CAUSE CHAIN (2026-10-27, hypothesis, contradicted in part by the correction above; supersedes the window and overhead paragraphs below where they conflict):** (1) Minas (platform) confirmed luna and luna-pro both have a 1.1M window. Kibana's `getContextWindowSize` resolves it from `config.providerConfig.model_id` against `known_models` (substring match): local `gpt-5.6-luna` and `gpt-5.6-luna-pro` match `gpt-5.6-luna` (1.05M) so local evals never compact and substitution (100k) works; c0 runs `gpt-6-luna-pro` (EIS model_id `openai-gpt-6-luna-pro`), which matches nothing, so it falls to `DEFAULT_CONTEXT_WINDOW` 128k (compaction >102k real tokens, and compaction wins over substitution). (2) `compactContext` keeps a 40k-est-token tail (chars/4 estimate) plus the pinned last cycle; with less history than that there is nothing to cover and it no-ops, and a skipped compaction still sets `lastContextActionCycle` (5-cycle cooldown), so neither compaction nor substitution runs while context keeps growing. It only succeeds once est history exceeds ~43k, which is why c0 compaction `token_count_before` never goes below 43.5k and why the pasted 3-rule run compacted at est 50.7k / real 208k (71k fixed overhead + luna-pro's ~1.3 chars/token vs the est's chars/4). (3) luna-pro reports ~3.5x more input tokens than luna for identical text (cause unknown), so the 102k line is crossed after ~30k of real tool output. Fix candidates (separate change, not the prompt): add `gpt-6-luna`/`gpt-6-luna-pro` to known_models, or make `getContextWindowSize` read EIS `metadata.capabilities.context_window.max_input_tokens` (1.05M declared); with 1.05M, compaction line 840k and substitution still at 100k, same as local. Verified: code at c0 build d6530bc5778c has an empty diff vs our base for inference-common/connectors and agent_builder execution.

**Fixed per-call overhead + estimator gap (2026-10-26, measured from c0 traces, supersedes the window hypothesis below):** the FIRST luna-pro call of a run, before any tool result, is already 64-72k input tokens (median 72k over 192 runs). Its parts (one trace): system instructions 60.9k chars (workflow 22k, incident_matching 7k, tools 3.5k), tool definitions 62.6k chars across 18 tools, of which `events_write` is 30.3k chars (27.8k schema, 19.9k of it field descriptions: summary 2.9k, severity 2.3k, symptom_hypothesis 2.0k, assessment_note 1.8k, title 1.4k; none duplicated in the system prompt). Real tokens are ~1.7-1.9 chars/token on these payloads vs the harness estimator's chars/4: the pasted 3-rule batch compacted with est `token_count_before` 50,765 while the real call input was 208.5k (71k overhead + ~137k history). Calls of 117k, 169k, 186k, 188k, 197k ran with no action, so a 128k window (threshold 102k) does NOT explain it; across 35 compactions (summarizer-call pattern) the trigger input ranged 178k-520k+, median ~450k, and 52 other drops (substitution) 189k+, so the real threshold/window is still unidentified. Cached tokens are counted in input_tokens (sum of per-call trace values equals model_usage.input_tokens exactly). Levers that are prompt-side: shrink the 62k-char tool schema (events_write descriptions) and the 61k-char system prompt, both paid on every call.

**Model comparison on identical prompts (2026-10-26, local evals, commit ec25ec4d; luna = gpt-5.6-luna 14:00-15:46Z, part of it the stale-code window; luna-pro = gpt-5.6-luna-pro 17:35-18:19Z):** same system prompt (60.8k chars) and tool schemas (58.4k chars), yet reported input tokens per call are ~3.5x higher on luna-pro: chars/token 4.46 (luna) vs 1.29 (luna-pro), first call 26k vs 94k tokens. Per eval run input tokens: bank-of-anthos 255k vs 596k, continuation-inactive 482k vs 1.58M, active 449k vs 1.77M, with similar tool-call counts (10-12, 19-22). Output tokens 2-3x too. luna-pro is not worse on scores (n small: discovery luna-pro n=10 reps vs 20): confirmation_alignment 1.0 vs 0.56, grouping_correctness 1.0 vs 0.32, topology_correctness 0.92 vs 0.63, severity_calibration 0.84 vs 0.92. So the compaction trigger on c0 (luna-pro) is driven by luna-pro's token accounting being ~3x luna's for the same text, which local luna evals cannot show; luna evals reach ~46k max input, luna-pro 150k median / 216k max. Whether luna-pro's counts are real tokenization or inflated reporting is unknown.

**Older window hypothesis (2026-10-26, REFUTED for the pasted run; connector comparison was confounded):** the c0 connector `.openai-gpt-6-luna-pro-chat_completion` advertises `metadata.capabilities.context_window.max_input_tokens = 1,050,000` (EIS), but `getContextWindowSize` (inference-common `connector_capabilities.ts`) only reads `config.contextWindowLength` or `known_models` (no gpt-6 entry) and ignores that field, so Agent Builder falls back to `DEFAULT_CONTEXT_WINDOW` 128k (compaction 102k, substitution 64k); code path verified, connector `capabilities` is `{}`. Evidence that does NOT hold: gpt-5.4 rounds (177, 0 compactions) are from 10-21..10-23, i.e. an older prompt era, with median last-call input 72k vs 157k and 8 vs 10 LLM calls; claude-4.6 rounds (16) have median 2 tool calls and cannot compact (cooldown needs >=5 cycles). Correct luna-pro numbers: 35 of 123 rounds compacted (65 compaction events). Contradicting data: 42 of 75 non-compacted luna-pro rounds with >=8 tool calls ended with last-call input >150k, and 42% of compactions had est history <100k, so no simple 102k threshold reproduces the trigger. To settle: A/B the same batch and current prompt on luna-pro vs a known-window connector, or locally set `contextWindowLength` and replay a wide scenario. Candidate upstream fix: read EIS `context_window.max_input_tokens` or add gpt-6 to known_models.

**Root cause:** a run's sample rows (`execute_esql` LIMIT 5, ~140-216 columns, no KEEP by design) are 3-14k tokens each by source (agentless-api 14.4k, ams 12.6k, eis 10.3k, autoops 9.0k, control-plane 7.4k, cphosted 3.1k, sandbox 0.2k). Runs with >=100k sample tokens: 6 of 6 restarted, 17% wrote, median 18 min; <25k: 0 of 361 restarted. Old prompt sent all samples in ONE cycle (one 101.7k-token jump), so compaction fired before clearing could act. Profiling queries are ~3% of volume, not a cause.

**Compaction mechanics (code):** compaction at 0.8 x connector window, wins over substitution; 5-cycle cooldown after any action; substitution clears results >1k tokens except the last 2 cycles; summary is an LLM summary told to omit tool output (per-rule verdicts/KI payloads are lost, so the agent reloads the skill and re-fetches, a restart loop); tail <=40k verbatim; per-result cap 20k then preview only; `read_file` truncates at 10k tokens (no range); `summarizeToolReturn` applies to previous rounds only, not cycles inside a run. At c0: 33/160 conversations compacted (63 compactions, first after 13-28 tool calls, token_count_before as low as 43k), 27/160 had substitutions.

**Batching:** code default discovery batch size 3, maxReviewPasses 3 (review loop = fresh agent run per pass); c0 runs batch size 7. All >10 min runs had batch 7. User constraint (2026-10-26): do NOT rely on the review loop or a smaller batch setting; detection can hand discovery up to 10 detections in one run, so the in-run flow (per-rule cycles, sample footprint) must hold at 10 rules at c0 widths.

**Decisions (user):** do not prepare the agent for compaction, make the flow not trigger it; keep LIMIT 5 (fixed LIMIT/KEEP-by-name are c0-shaped patches); no attachment ledger; skill load and KI searches once per run; sequential per-rule flow (sample, read+write findings, profile, next rule) already in the working tree; KEEP by hypothesis rejected (info loss); investigator avoids context via sandbox + jq, not applicable.

**Column facts (1,029 c0 samples):** same-field twins (.keyword/.text) 11.1% of chars, twin values always a subset of base (0 violations in 37k row comparisons); host.ip+host.mac 37.2% overall (65% autoops, 0% cphosted), one-to-one with host.name in 98.4%; exact-duplicate columns under different names 9.2%; ES|QL KEEP has no exclusion syntax; DROP of an unknown column is a hard error (probe first with `KEEP prefix* | LIMIT 0`).

**Eval hygiene:** the server must be restarted to load prompts AND tool code; verify by grepping trace system prompt/skill for a marker string from the latest edit (a 15:04Z batch ran stale code).

**Why:** user wants the discovery agent never to hit compaction at c0. **How to apply:** judge any change by per-cycle token growth and sample tokens per run, not by turn count alone.
